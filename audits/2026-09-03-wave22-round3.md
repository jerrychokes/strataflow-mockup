## Part 1 — round 2's two findings

### W22-R2-1 (P1, closed by round 2) — re-verified, and the fix is real

Built page:

```
$ grep -o '<button[^>]*>Amend the programme</button>' index.html
<button type="button" class="mk-btn" disabled title="No version for an amendment to
create — 3 of the 5 fields a version needs have nowhere in this record to come
from">Amend the programme</button>
```

`disabled` is present. `title` names the reason with derived numbers: `versioning
.short.length` (3) and `VERSION_FIELDS.length` (5) are both getters over
`versionEvidence`/`VERSION_FIELDS` (`seed.mjs:12877-12921`), not typed — confirmed by
reading the getters, not by trusting the string. `.mk-btn[disabled]` (`chrome.mjs:295`,
`opacity:.45; cursor:not-allowed`) is an attribute selector and matches a boolean
`disabled` with no value; confirmed in a real Chromium page: `matches('.mk-btn
[disabled]')` → `true`, computed `opacity: "0.45"`, `cursor: "not-allowed"`. The fix is
real and does what round 2 said.

**But the disclosure the commit message claims is narrower than it reads, and testing
it found something worth recording.** A native HTML `disabled` button is removed from
the tab order entirely — not "sometimes skipped," structurally unfocusable. Proved in
a real browser rather than asserted:

```js
btn.focus();
document.activeElement === btn   // → false
```

Calling `.focus()` on the element directly does not move focus onto it. A keyboard or
screen-reader user tabbing through this screen will never land on this button at all,
disabled or not, so the `title` — the one place the derived "3 of the 5" now lives —
is unreachable to them regardless of whether their screen reader announces `title`
text (which round 2 already flagged most don't). The commit message's "the reason is
on the button itself rather than only in this sentence" is true only for a sighted
mouse user hovering it.

This does **not** reopen W22-R2-1, because the substance isn't actually lost: the card
body immediately above the button, in ordinary reading order, already states "3 of
the 5 fields have nowhere in this record to come from" as a getter-derived sentence
(`screens.mjs:5735`) before a reader ever reaches the button — so an AT user reading
the card in document order gets the number before the control, not instead of it. The
button's own `disabled`+`title` is a real, correct improvement for sighted users and a
no-op for keyboard/AT users, who were already served by the paragraph. Recorded as an
honest limitation of the fix's own framing, not a defect — no ID assigned, not
blocking.

### The catalogue-wide check the brief actually asked for

Every `C.btn(` call (45) and every `C.blastRadius(` call (30) in `screens.mjs` was
read for a write-promising label paired with prose on the same screen that states,
in the present tense, that the action cannot currently succeed on this record —
the exact shape W22-R2-1 fixed. Most of the catalogue is fine and consistently so:

- Five other sites already use `{ disabled: true, title }` (`screens.mjs:1844, 1864`,
  plus `#qaqc`'s "Advance to validated" whose title is itself a derived getter over
  `D.needDecision`), a `Save changes` disabled-until-dirty button with no title
  (ordinary form UX, not a "cannot" claim, doesn't need one), and two disabled
  checkboxes with their own self-explaining labels.
- Three `C.blastRadius` sites (`screens.mjs:5516, 5695, 5993`) refuse in the action
  label itself — `action: 'Not available — the amendment is staged'` — which round 2
  correctly called a deliberate, consistent, more-explicit-than-`disabled` convention.
- The data explorer's 39 enabled selects (W20-A-4's ground) carry a page-level notice
  stating nothing on the screen filters; correctly out of scope here, since that is a
  *view* control and this check is about writes, exactly as the round-2 commit message
  distinguishes.

**One did not fit that pattern, and it is a genuine sibling of the case just fixed.**

**W22-R3-1 (P1) — `#field-capture`'s "Mark the round complete" is enabled while the
screen states, today, that it cannot succeed.** `roundPreflight()` (`screens.mjs:1536
-1595`) computes `blocking` from live preflight counts and, when non-empty, renders:

```
The round cannot be marked complete yet — 2 things hold it.
```

— on the built page right now (`grep -o "The round cannot be marked complete yet[^<]*"
index.html` → exactly that, with "2" derived from `P.pendingRecords`/`P.postChecked`).
Immediately below it, `C.blastRadius({ action: 'Mark the round complete', ... })`
renders:

```
$ grep -o '<button[^>]*>Mark the round complete</button>' index.html
<button type="button" class="mk-btn mk-btn--primary">Mark the round complete</button>
```

No `disabled`. No `title`. No refusal in the label, unlike the three `blastRadius`
sites that do state it there. A full-opacity, focusable, primary-styled button with a
plain imperative label, sitting directly under a sentence that says, on the same
screen, in the present tense, that pressing it cannot work. This is the shape the
round-2 commit fixed at `#programme`, reproduced exactly: a control that promises what
the screen has just finished explaining it cannot do.

`#field-capture` carries `now: 'proposed'` in the register (`screens.mjs:14217`), the
same category as `#programme` — this is not a real-product `sf-` screen standing in
for behaviour outside this catalogue's remit; it is `mk-` proposal content, squarely
inside the boundary the fix at `#programme` was accountable to.

**The screen argues against disabling it, in a comment predating the fix by three
waves** (`git log -S "greyed-out button that will not say why"` → `8a95b94`, "Wave 6:
field capture and QA/QC redesigned to the practitioner review"):

> "The control below states what it would write and stays refusable rather than
> silently disabled: a greyed-out button that will not say why is how a field officer
> at a gate loses an afternoon."

Weighed fairly: there is a real distinguishing argument available and the wave never
makes it. `#programme`'s blocker (no version field exists anywhere in the schema) is
permanent — nothing short of a product change resolves it, ever. `#field-capture`'s
blocker (two pending device syncs) is transient and could clear within the same visit
as connectivity returns, which is a genuine reason a field officer might want to keep
pressing a live control rather than watch a permanently greyed one. That argument, if
made, would be a real basis for treating the two differently. But it is not the
argument the comment makes, and the argument the comment *does* make — "a greyed-out
button that will not say why" — is precisely the problem the `disabled`+`title`
convention (used five other places in this same file, and now a sixth at `#programme`)
solves: a disabled button with a title **does** say why. The Wave 6 rationale predates
that convention and was never revisited against it. Whatever the right answer is, the
catalogue does not currently apply one rule: before this wave's fix, both buttons were
consistent with each other (both silent); after it, `#programme` explains itself on
its own face and `#field-capture` does not, for two structurally identical claims.
**The round-2 fix made the catalogue less consistent, not more** — exactly the finding
the brief invited.

`c.held.length` and `c.present.length` each drive a bare, unpluralised verb. Proved by

Nothing else in the diff read as a fix breaking something — the MW09-camp split

### 2. `#completeness` and `#programme` at 375px — one is fine, the other is not usable

Screenshots taken directly against the built page (`playwright-core`, real Chromium),
scoped to each table's `.sf-table-scroll` region rather than the whole screen.

**`#completeness`'s six-stage table: correctly built, genuinely usable at 375px.** Its
sticky first column ("Planned"/"collected"/…) is 100px wide against a 306px visible
pane — comfortably narrower than the viewport. Scrolling reveals the third column's
actual numbers ("7 locations the round expects", "3 distinct suite names…") with the
stage label staying pinned as an anchor, exactly as `app.css`'s sticky-column comment
intends. At 1280px it needs no scroll at all and reads cleanly.

**`#programme`'s §6.2 attribute table: not dense — structurally unreachable.**
Measured directly against the live DOM:

| Table | Container width | Sticky (1st) column width | Total table width | Columns |
|---|---|---|---|---|
| §6.2 — 10 programme attributes (`#programme`) | 306px | **1378px** | 2802px | 5 |
| What each object holds of a version (`#programme`) | 274px | **497px** | 1111px | 4 |
| §6.3 — preparation items (`#events`, the W22-R2-2 destination) | 306px | **1461px** | 2767px | 4 |
| Six stages of the round (`#completeness`, for comparison) | 306px | 100px | 1152px | 3 |

The §6.2 table's sticky first `<th>` — `<strong>Attribute</strong><small>note</small>`
— is **4.5× wider than the visible pane**. `.sf-table--matrix { min-width: max-content
}` sizes the column to its longest unwrapped note line; `.sf-table--matrix tbody th {
position: sticky; left: 0; z-index: 1; background: var(--sf-ground) }` then pins that
1378px-wide, opaque column to the left edge of a 306px viewport on every scroll frame.
Because the sticky element is wider than the viewport itself, it paints over the
*entire* visible area regardless of scroll position — not "until you scroll," at every
position. Proved directly:

```js
el.scrollLeft = el.scrollWidth;   // scroll all the way to the end
// second column's visible fraction inside the viewport, at maximum scroll:
0%
```

At the furthest possible scroll, zero pixels of the second column ("Required by") are
visible — and since a sticky element's rendered position relative to the scrollport is
identical at every scroll offset once "stuck," 0% at max scroll means 0% at every
scroll position. A reader on a phone sees the attribute names and their notes and
**never** sees "Required by," "Verdict," "What each programme holds," or "Where it
lives instead" — the entire payload of the table — for any of the ten rows, no matter
how they scroll. This is not the density round 2 correctly waved off for the
`#hydrochem` plate-claims card ("findable, not buried … dense … not a defect"); it is
zero-percent reachable.

**This is not a one-off.** The identical `<strong>+<small>` first-column pattern
produces the identical defect on two more matrix tables, both added in this wave
(confirmed against `git diff 36f71e3 25ea159`, both are `+` lines): the versioning
"fields vs. objects" table (497px sticky column against a 274px pane) and, worse, the
`#events` §6.3 preparation-items table (1461px against 306px) — which is exactly the
screen W22-R2-2's new forward link sends a reader to. A mobile reader who follows that
link, scrolls 41–45% down the screen to find the promised section, and reaches the
table it was pointing at, finds it unusable for the same structural reason.

**W22-R3-2 (P1) — three Wave-22 matrix tables are unusable on a 375px viewport, and
the check that could have caught this exists but is scoped to one screen.**
`verify.mjs` contains a sticky-matrix check (lines 102–121) that explicitly tests
"the row-identity column must stay put" during a scroll — but it is hardcoded to
`#crosstab` only (`document.querySelector('#crosstab .sf-table-scroll')`), so it never
ran against any of Wave 22's new tables. And its own assertion — that the sticky `th`
does not move during scroll — would not have caught this failure mode even if
generalised: the column here *does* stay put correctly; the defect is that "put" covers
the entire viewport. `verify.mjs`'s clean run ("no document overflow at any width …
matrix panning intact") is true and is not the same claim as legible, exactly as this
round's brief predicted.

## Verdict

**Wave 22 does not pass the round-3 gate.** Two P1s are open: W22-R3-1 (an enabled
write-promising control contradicting its own screen's present-tense refusal,
pre-existing since Wave 6 but made inconsistent by this wave's own fix to its sibling)
and W22-R3-2 (three of this wave's own new matrix tables are completely unusable at
375px, not merely dense, with a verification gap — a check for exactly this shape
exists and is scoped to one unrelated screen). Both are new findings from ground round
1 and round 2 had no occasion to examine (a catalogue-wide control sweep; a
DOM-measured, mutation-proved mobile-legibility check) rather than re-opened prior
findings — every finding both earlier rounds closed is re-confirmed closed here.

§11 caps this wave at three rounds and this is the third. Per the same mechanism
Wave 21 used at its own cap: the wave closes here with two P1s open rather than
looping to a round that does not exist, to be fixed in the closing response and
verified as carried riders on Wave 23's round 1 — not by a round 3 auditor who no
longer has a round 4 to re-check the fix.

Both open findings have small, mechanical fixes available: `C.btn('Mark the round
complete', 'primary', { disabled: true, title: '...' })` (or the `blastRadius` label
convention already used three other places) for W22-R3-1; either wrapping the note
`<small>` in a width-constrained span so the column stops sizing to its longest
unwrapped line, or moving the note out of the sticky cell, for W22-R3-2 — applied to
all three affected tables, not only the one this round measured first. W22-R3-4 and
W22-R3-5 are dormant and lower priority than either P1, but sit in exactly the defect
class this wave's own retrospective is about and are one-line fixes each.
