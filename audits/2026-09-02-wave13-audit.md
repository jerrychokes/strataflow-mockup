## Findings

### W13-A-1 · P1 — `#package` still counts the two refused formats as exportable, one panel below the settlement that refuses them

- **Reproduction:** render `#package`. The held-here panel reads *"EDD format definition ·
  revision · 2"*, states *"An item that declares no version is refused, never defaulted"*,
  names `ESdat legacy export` and `EQuIS EDD (4-file)`, and says of the old counting that it
  *"was this panel disagreeing with itself"*. The next panel down ("The other direction —
  building one here") reads **"9 items this instance could export … EDD format definition ·
  4 · The format registry"**, captioned *"Counted off the registers themselves"* — the exact
  counting rule the settlement just corrected, on the same screen, for the same kind. In
  source: `exportable` computes `exports: … FORMATS.length` (`seed.mjs:8785-8788`) while
  `KINDS.held` reads `CONFIG_INVENTORY` three declarations above.
- **Why it is wrong and not merely different:** by the settlement's own anchor,
  `configBundle()`/`versionOf()` **throws** on an unversioned artifact
  (`config-bundle.ts:97-108`) — an export built from this instance could not carry those
  two rows, so "could export … 4" is false under the rule quoted verbatim beside it, and
  "9 items this instance could export" should read 7. The record's own sentence — *"they
  are formats the migration was read with rather than configuration this deployment
  holds"* — says the instance does not hold them; what it does not hold it cannot export.
  The panel's "what it would refuse" prose covers only customer data and never reconciles
  the 4 against the 2.
- **Affected acceptance criterion:** *"the four disagreements each resolve to one source
  read N times"* — the EDD-format count now renders from **two** sources on one screen
  (`CONFIG_INVENTORY` → 2, `FORMATS.length` → 4). A reader finds two counts of one kind,
  which is the state the settled note says it exists to prevent. Noted fairly: the wave
  spec itself ordered *"verify neither moved"* for `exportable`, so the implementation
  followed its instructions — the instruction and the settlement conflict, and the fix
  round may need to amend the spec rather than just the seed.
- **Recommended correction:** derive `exportable`'s EDD count from `CONFIG_INVENTORY` (with
  the two refused rows named beside it, exactly as held-here now does), or — if register
  liveness is the point — rename and recaption the panel so it counts register rows rather
  than claiming exportability, and state on it why two of them could never leave. Then
  re-verify `#exchange` and any other reader.

### W13-A-2 · P3 — the truncation claim contradicts itself in the seed record

`seed.mjs` (above `CONFIG_INVENTORY`): *"twelve hex characters of a SHA-256, shown
truncated exactly as the product's own manifest renders one (`sha256.slice(0, 16)`)"* —
the citation is real (`diagnostics.ts:457` slices 16), but twelve is not sixteen, so the
digests are *not* truncated "exactly as" the product renders them. Unrendered — the
sentence lives only in the seed comment. Fix the sentence (or the digests) either way.

### W13-A-3 · P3 — the post-as-at date classification omits `#package`'s "if activated" preview dates

The two-clocks record classifies every rendered date after `OPS_AS_AT` as the four named
event records plus "due dates, contract terms, upgrade windows, a holding-time expiry and
this wave's own settled-notes". The auditor's own enumeration found two renderings of
`2026-09-01` on `#package` — *"2018-08-01 → 2026-09-01 → if activated"* and *"Activating
version 2026.1 on 2026-09-01"* — which are hypothetical action dates, none of the stated
classes (and rightly not among the four *records*). The classification sentence should name
the class, since the record's own lesson is that the first draft missed a date by recalling
instead of enumerating.

### W13-A-4 · P3 — two corrected numbers print their before-state everywhere except on a screen

The imports tiles print their old literals on the screen; `#package` prints "held here: 4"
in its settled note; `#entitlement` renders the old 4-rows-vs-8-rows list shape. But the
bundle size (3.6 MB) and the old exclusion count (2) appear in the README and the seed
record only — `index.html` contains no "3.6" and no rendered old exclusion count, while the
corrected values (3.1 MB, 6 exclusions) render. Uneven application of the wave's own
"printed with what they said before" convention; history is preserved, just not where the
number is.
