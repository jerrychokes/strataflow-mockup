**The harder question — nothing verifies `mentions` against the repository, is that
acceptable?**

Confirmed: `build.mjs` never shells to `git`, and no guard anywhere checks
`detectionFrequency.mentions` against source. My own mutation above proves it —
I invented a *fictional* third mention (a file/reason with no real basis) and the
build accepted it silently, printing "3 times" with a fabricated occurrence and no
complaint. In that literal sense, this is "the same shape one level up": a hand-typed
array that a human has to have gotten right, exactly like the four hand-typed numbers
that caused W22-M-3 in the first place.

**My view: it is not the same *risk*, even though it is the same *shape*, and the fix
is proportionate rather than incomplete.** Three reasons:

1. **The quantity being recorded is frozen, not live.** `plateClaimCount` and
   `stageReadings` guard against *mutable* data (a seed array that changes wave to
   wave) drifting out from under a typed number — that is the actual failure mode
   the wave-21 retrospective is about. `detectionFrequency.mentions` describes how
   many times a phrase occurred in tracked source **before a specific, already-passed
   commit** (`cfdb910`). That commit cannot un-happen; the fact it records cannot
   drift the way `ARSENIC_MW05.length` can. There is nothing for a build-time guard
   to *re-derive from*, because the state being described no longer exists in the
   working tree (the "nowhere"/"once" surfaces were edited away in later commits) —
   you cannot `grep` your way back to it without shelling to git history, which
   `build.mjs` does nowhere else in this codebase.
2. **It was independently checked, twice, against the actual history.** Round 1's
   mechanical audit ran `git log -S` and direct `git show <hash>:<file>` against the
   baseline and got exactly 2 hits, matching the array. I independently re-ran
   `git show cfdb910:seed.mjs` and `git show cfdb910:VENDOR_REQUIREMENTS.md` for this
   round and got the identical two occurrences, with wording that matches each
   `was` string almost exactly (*"detection frequency and exceedance frequency have
   no surface at all"* in the catalogue's own note; *"- Detection frequency"* as a
   line in the brief). The number was never actually in question at any point in this
   wave's history — only which of four typed *surfaces* echoed it correctly.
3. **A live-data guard would be a heavier, newer kind of dependency than anything
   else in this build**, and the risk it would close (a hand-edit to this one array
   being wrong, going forward) is narrower than the risk it closed already (four
   independently hand-typed numbers disagreeing with each other on the same page,
   which is what actually happened and is what a reader could see with their own
   eyes). Collapsing four typed numbers into one typed record is a real reduction in
   surface area even without a git-backed guard: a future editor who *does* want to
   add a mention now has exactly one place to get it right instead of four, and
   getting it wrong produces a self-consistent falsehood rather than a
   self-contradicting one — worse than derived-and-guarded, better than
   typed-four-times-independently.

**Verdict: accept as fixed for what W22-M-3 actually found (four disagreeing
surfaces); the residual manual-trust point is real but proportionate, and I would not
block the gate on it.** If this "how many times did X appear before commit Y" pattern
is ever copied for a different measure, that is the point at which a shared
`git show <baseline>:<file> | grep -c` helper (cached, since the baseline is
immutable) would earn its cost — a single instance, already cross-checked by two
independent audits against the actual git history, does not.

## Part 2 — what round 1 did not cover

### 1. Drawn controls on `#programme` and `#completeness` — one genuine violation

Every control on both screens was enumerated by reading `programme()`
(`screens.mjs:5640-5811`) and `roundCompleteness()` (`screens.mjs:10220-10397`) in
full, then checked against the codebase's own established convention for an
unavailable control. That convention exists and is used correctly elsewhere:
`btn(label, kind, { disabled: true, title })` is called with `disabled: true` at
`screens.mjs:1844`, `1864`, `12544`, `13029`, `13035`, and `.mk-btn[disabled]` gets
real, distinct CSS (`opacity: .45; cursor: not-allowed;`, `chrome.mjs:295`) — a
disabled control in this catalogue is visually and semantically marked, not merely
described in nearby prose.

**`#programme`'s "Amend the programme" button violates that convention. P1.**
`screens.mjs:5752`: `C.btn('Amend the programme')` — no third argument, so
`disabled` defaults to `false`. Rendered:

```html
<button type="button" class="mk-btn">Amend the programme</button>
<span class="mk-muted">The control is present and does nothing, which is the honest
state: there is no version for an amendment to create.</span>
```

The button is a normal, full-opacity, hover-responsive, focusable, clickable control
with a plain actionable label. Nothing in its own markup — no `disabled` attribute,
no `aria-disabled`, no dimmed styling, no `title` tooltip — discloses that it does
nothing; only the adjacent prose does, and a keyboard or screen-reader user tabbing
to the button hears "Amend the programme, button" with no indication of
unavailability. This is exactly the shape the brief names: *"a control that promises
what the screen has just finished explaining it cannot do."* The tool to mark it
correctly exists and is used five other places in this same file — this is an
omission, not a missing capability. **Fix is one line:** `C.btn('Amend the
programme', '', { disabled: true, title: 'No version for an amendment to create — see
below' })`.

**`#programme`'s stand-down refusal (`C.blastRadius`) is not a violation, and is a
repeated, deliberate convention.** `screens.mjs:5695`:
`action: 'Not available — the stand-down condition is not met'`. `blastRadius`'s
signature (`controls.mjs:525`) has no `disabled` parameter at all — its `action`
button is always rendered `mk-btn mk-btn--primary`, and the refusal is baked directly
into the button's own visible label rather than into its enabled/disabled state.
Checked whether this is a one-off or an established pattern:

```
$ grep -n "action: 'Not available" screens.mjs
5516:      action: 'Not available — the amendment is staged',
5695:      action: 'Not available — the stand-down condition is not met',
5968:      action: 'Not available — the amendment is staged',
```

Three sites use this exact convention. Unlike "Amend the programme," no reader can
mistake this button as functioning — the unavailability is stated on its face, in
its own primary-styled text, more explicitly than a bare `disabled` attribute would
be (which signals *that* something can't be done but not *why*). Worth a P3 note that
`blastRadius` could grow a `disabled` option for visual consistency with `C.btn`
elsewhere, but it is not a falsehood and not new to this wave.

**No "version control" or "owner assignment" control was found anywhere on either
screen beyond the one above** — both functions were read in full; the only other
controls are honest navigation (`<a class="mk-btn" href="#...">`) to `#completeness`,
`#field-capture`, `#dqa`, `#import-review`, and a decorative round-selector
`C.segmented(...)` on `#completeness`'s toolbar. That segmented control has no
`data-target` wiring (its options are plain strings, not `{label, target}` objects)
so clicking "2026 Q1 · GW-QTR" does nothing — but this is true of **every**
`C.segmented` call in the whole mockup (checked all 8 call sites; none passes a
`target`), so it is a general property of this static prototype's chrome rather than
a `#completeness`-specific defect, and it is a view-toggle rather than a
write-promising control, which is a materially different kind of claim than "Amend
the programme." Not flagged as a finding.

round.
